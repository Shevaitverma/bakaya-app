#### B1. Google sign-in always fails on native: id_token read from raw promptAsync result, but native uses code flow
- **Where:** `mobile/src/hooks/useGoogleSignIn.ts:72` · **Platform:** both · **Domain:** auth
- **What happens:** signIn() awaits promptAsync() and reads result.params.id_token. In expo-auth-session 7.0.10, Google.useAuthRequest defaults responseType to Code on any non-web platform (installed app), so the raw promptAsync result contains only params.code — the id_token only appears later in the hook's second return value (fullResult) after an async auto-exchange effect, which this hook discards as `_response` (line 45). Failure scenario: user taps 'Sign in with Google' on Android or iOS, completes the consent screen successfully, and the app always throws 'No ID token received from Google'. Google SSO can never succeed on mobile. Fix requires either responseType: 'id_token' in the request config or consuming the exchanged `response` object instead of the promptAsync return value.
- **Trace:** mobile/src/hooks/useGoogleSignIn.ts:61 (promptAsync) -> node_modules/expo-auth-session/build/providers/Google.js:132-138 (responseType=Code on native) -> raw result.params = { code } only; exchanged id_token lands in fullResult via Google.js:182-211 which is the ignored `_response` (useGoogleSignIn.ts:45) -> useGoogleSignIn.ts:72-74 throws 'No ID token received from Google'
- **Root cause:** mobile/src/hooks/useGoogleSignIn.ts:61-74 — signIn() reads id_token from the raw promptAsync() result, but on native the request is a code flow (expo-auth-session Google.js:132-138 defaults responseType to Code on installed apps), so the raw result only contains params.code; the exchanged id_token lands in the hook's second return value which is discarded at useGoogleSignIn.ts:45.
- **Fix:** In useGoogleSignIn.ts, keep the request object (const [request, , promptAsync] = Google.useAuthRequest(...)) and, inside signIn() after result.type === 'success', exchange the code directly: const tokens = await exchangeCodeAsync({ clientId: request!.clientId, redirectUri: request!.redirectUri, code: result.params.code, extraParams: { code_verifier: request?.codeVerifier ?? '' } }, Google.discovery); then use tokens.idToken in place of result.params.id_token. This mirrors the library's own auto-exchange while preserving signIn's promise contract; both call sites (LoginScreen, RegisterScreen) route through this single function. Note: responseType 'id_token' is not a safe alternative because Google installed-app client types reject implicit flows.

#### B2. Release builds ship with API base URL pointing at localhost / 10.0.2.2
- **Where:** `mobile/src/constants/api.ts:25` · **Platform:** both · **Domain:** platform-infra
- **What happens:** getBaseUrl() resolves: (1) EXPO_PUBLIC_API_URL — only .env.example is committed and eas.json defines no `env` for any build profile, so EAS builds get nothing; (2) Constants.expoConfig.hostUri — only set when served by the Expo dev server, undefined in standalone builds; (3) fallback http://10.0.2.2:8080 (Android) or http://localhost:8080 (iOS). Failure scenario: any `eas build --profile production` (or preview) produces an app where every network call targets the device's own loopback / the emulator-host alias — the app is 100% non-functional for real users on both platforms. The API URL for production must be baked into eas.json env or app.json extra.
- **Trace:** mobile/src/constants/api.ts:12-27 (fallback chain) -> mobile/eas.json:5-24 (no env block in any profile) -> mobile/.env.example (real .env untracked, not uploaded to EAS)
- **Root cause:** No production API URL is supplied to release builds: mobile/eas.json:13-24 (preview/production profiles lack an env block) combined with the silent loopback fallback at mobile/src/constants/api.ts:24-26.
- **Fix:** Add the production URL to the release profiles in mobile/eas.json — e.g. "preview"/"production" each get "env": { "EXPO_PUBLIC_API_URL": "https://api.<prod-host>" } — getBaseUrl() already reads it first, so all callers are fixed in one place. Optionally harden api.ts: in getBaseUrl(), if (!__DEV__) throw new Error('EXPO_PUBLIC_API_URL not set') before the loopback fallback, so a misconfigured release build fails loudly at startup instead of silently targeting localhost.

#### B3. DateRangePicker custom inputs fire an API fetch on every keystroke with partial/invalid dates
- **Where:** `mobile/src/components/DateRangePicker.tsx:131` · **Platform:** both · **Domain:** analytics-categories
- **What happens:** handleCustomStartChange/handleCustomEndChange call onChange(value) on each keystroke with no format validation. Typing '2026-07-01' therefore sends startDate='2', '20', '202', ... to GET /personal-expenses; the server's zod schema requires YYYY-MM-DD, so each keystroke returns 400 BAD_REQUEST, which the screen surfaces as an error state/alert while the user is still typing, and floods the rate limiter (100/min shared). There is also zero validation of the final value (e.g. '2026-13-45' or '07/14/2026' is sent as-is). Web's equivalent uses <input type='date'> which only emits complete valid dates and enforces min/max cross-constraints. Also keyboardType 'numbers-and-punctuation' is iOS-only, so Android shows a full text keyboard.
- **Trace:** DateRangePicker.tsx:131-139 (onChange per keystroke, no validation) -> ProfileExpensesScreen.tsx:138-143 (handleDateRangeChange -> fetchExpenses(newStart,newEnd) immediately) -> server zod YYYY-MM-DD regex -> 400 -> ProfileExpensesScreen catch sets error/alert per keystroke
- **Root cause:** mobile/src/components/DateRangePicker.tsx:131-139 — custom date inputs emit onChange on every keystroke with no completeness/format validation, despite the component having an Apply button (line 141) that already re-emits the selection. Secondary trust-boundary gap: server/src/schemas/expense.schema.ts:31-32 accepts any string for startDate/endDate, turning garbage input into a mongoose CastError 500 via parseISTDate (server/src/utils/date.ts:24-27).
- **Fix:** In DateRangePicker.tsx: delete the onChange calls from handleCustomStartChange (line 133), handleCustomEndChange (line 138), and the custom branch of handlePresetPress (line 123) — the text handlers should only setState. Apply (handleApply, line 141) becomes the single emit point for custom ranges, gated by a completeness check: const isValidDate = (s: string) => /^\d{4}-\d{2}-\d{2}$/.test(s) && !isNaN(new Date(s).getTime()); in the custom branch emit only values passing isValidDate (pass undefined otherwise, or disable Apply while invalid). This is one fix at the component all consumers route through. Trust-boundary hardening (server): change expense.schema.ts:31-32 to z.string().regex(/^\d{4}-\d{2}-\d{2}$/).optional() so malformed dates return a clean 400 instead of a mongoose CastError 500.

#### B4. Android OAuth redirect scheme com.bakaya.app never registered — browser cannot return to the app
- **Where:** `mobile/app.json:7` · **Platform:** android · **Domain:** auth
- **What happens:** expo-auth-session's Google provider builds the native redirect URI as `${Application.applicationId}:/oauthredirect` = com.bakaya.app:/oauthredirect. app.json only declares scheme "bakaya", and Expo's Android Scheme config plugin registers intent filters ONLY for config.scheme / android.scheme (it does not auto-add the package name, unlike iOS where Scheme.js explicitly pushes ios.bundleIdentifier as a CFBundleURLScheme). Failure scenario: on an Android standalone/EAS build, after the user completes the Google consent screen, Chrome tries to open com.bakaya.app:/oauthredirect, no activity matches the scheme, the redirect dead-ends in the browser, and promptAsync resolves as 'dismiss' — the user is silently bounced back with no sign-in. Fix: add "com.bakaya.app" to the scheme array (or android.scheme).
- **Trace:** node_modules/expo-auth-session/build/providers/Google.js:144-148 (redirectUri = applicationId:/oauthredirect) -> node_modules/@expo/config-plugins/build/android/Scheme.js:30-44 (only config.scheme added; package NOT added) vs ios/Scheme.js:38-39 (bundleIdentifier auto-added on iOS) -> mobile/src/hooks/useGoogleSignIn.ts:63-68 (result.type 'dismiss' -> silent return null)
- **Root cause:** mobile/app.json:6 — "scheme": "bakaya" does not include the Android applicationId "com.bakaya.app", and Expo's Android Scheme config plugin (node_modules/@expo/config-plugins/build/android/Scheme.js, setScheme) registers only config.scheme/android.scheme, unlike iOS which auto-adds the bundle identifier (ios/Scheme.js:37-40). So no Android intent filter matches expo-auth-session's Google redirect URI com.bakaya.app:/oauthredirect (built at node_modules/expo-auth-session/build/providers/Google.js redirectUri memo, returned verbatim by AuthSession.js makeRedirectUri lines 70-76 in EAS builds).
- **Fix:** In mobile/app.json change line 6 to "scheme": ["bakaya", "com.bakaya.app"] and rebuild (prebuild regenerates the manifest). Single root-cause fix: the Android Scheme plugin registers an intent filter for every entry in the array, making com.bakaya.app:/oauthredirect resolvable; iOS is unaffected since the bundle identifier scheme is already auto-added there.

#### B5. Screens pass stale AuthContext accessToken as explicit override — every request after first token expiry eats a 401 + full refresh round-trip
- **Where:** `mobile/src/context/AuthContext.tsx:62` · **Platform:** both · **Domain:** auth
- **What happens:** All screens (HomeScreen, GroupDetailScreen, etc.) pass the accessToken from AuthContext state into services, which forward it to authedFetch as a `token` override, bypassing the fresh token in storage (authedFetch.ts:212 `tokenOverride ?? storage.getAccessToken()`). When authedFetch's silent 401->refresh path rotates tokens, it only writes to storage (authedFetch.ts:114) — AuthContext state is never updated (refreshSession syncs state only when a screen explicitly calls it). Failure scenario: 15 minutes after login the context token expires; from then on EVERY service call sends the dead token, gets a 401, and triggers a brand-new /auth/refresh (the dedup only covers concurrent calls) — constant token rotation plus 2x latency per request, and it burns the server's 10 req/min auth rate limit (shared 'unknown' IP bucket when TRUST_PROXY is unset), producing 429s that feed the forced-logout bug below. Root fix: stop passing context tokens to services (let authedFetch read storage) or sync context state after every successful shared refresh.
- **Trace:** mobile/src/screens/Home/HomeScreen.tsx:142 (passes context accessToken) -> mobile/src/services/profileService.ts:18-21 (token override) -> mobile/src/lib/authedFetch.ts:212 (override wins over fresh storage token) -> 401 -> authedFetch.ts:217/114 (new tokens saved to storage only) -> mobile/src/context/AuthContext.tsx:47/136-163 (state never synced unless refreshSession explicitly called) -> next call repeats with same dead token
- **Root cause:** mobile/src/lib/authedFetch.ts:212 — authedFetch prefers the caller-supplied token override (sourced from never-resynced AuthContext React state) over the storage token that the silent 401-refresh path (authedFetch.ts:114) keeps fresh, so after the first access-token expiry every overridden request sends a dead token and triggers a fresh /auth/refresh round-trip.
- **Fix:** One line at the single choke point all services route through — flip the precedence in authedFetch.ts:212: `const initialToken = (await storage.getAccessToken()) ?? tokenOverride;`. Storage is always at least as fresh as context state (all state writes also write storage; silent refresh writes storage only), and the `?? tokenOverride` fallback covers the brief login window before saveTokens completes. No per-screen changes; the token params become vestigial and can be deleted later.

#### B6. Screens force logout when refreshSession returns false on transient network/5xx/429 refresh failures
- **Where:** `mobile/src/screens/Home/HomeScreen.tsx:230` · **Platform:** both · **Domain:** auth
- **What happens:** HomeScreen (also GroupsListScreen.tsx:68-102 and AnalyticsScreen.tsx:237 use the same pattern) catches a 401, calls refreshSession(), and calls logout() when it returns false. But refreshSession returns false for TRANSIENT failures too: performRefresh returns { ok:false, rejected:false } on network errors (authedFetch.ts:93), 5xx (authedFetch.ts:102), and 429 from the auth rate limiter — the exact cases the authedFetch design deliberately keeps the session alive for. Failure scenario: access token expired + flaky connectivity (original request reaches the server and 401s, the refresh POST times out or gets rate-limited 429) -> screen sees 401 -> refreshSession false -> logout() wipes storage and the query cache, permanently logging the user out on a network blip. Contradicts the documented invariant that only a server rejection of the refresh token ends the session; the screens should only propagate the error and let onSessionExpired handle true expiry.
- **Trace:** mobile/src/lib/authedFetch.ts:89-102 (transient -> rejected:false) -> authedFetch.ts:224 (401 propagates to caller) -> mobile/src/screens/Home/HomeScreen.tsx:228-232 (refreshSession false -> logout) ; refreshSession false path: mobile/src/context/AuthContext.tsx:141-158 (outcome.ok false -> return false, no rejected/transient distinction exposed)
- **Root cause:** Screens treat refreshSession()===false as an expired session, enabled by AuthContext.refreshSession (mobile/src/context/AuthContext.tsx:157) collapsing the rejected/transient distinction that performRefresh (mobile/src/lib/authedFetch.ts:93,102,110) exposes; call sites: mobile/src/screens/Home/HomeScreen.tsx:231-233, mobile/src/screens/Group/GroupsListScreen.tsx:89-91, mobile/src/screens/Analytics/AnalyticsScreen.tsx:231-233.
- **Fix:** Centralize session-ending in the shared refresh path: in performRefresh (authedFetch.ts:~99), call fireSessionExpired() when returning {ok:false, rejected:true} (and for the missing-refresh-token case at line 77), making it the single choke point for every refresh trigger (401-retry and proactive refreshSession alike). Then delete the now-redundant `else if (outcome.rejected) fireSessionExpired()` branch at authedFetch.ts:220-223 and remove the `if (!refreshed) await logout()` blocks in the three screens (keep the early return so the next focus cycle refetches). Transient failures then leave the session intact everywhere; genuine rejection logs out exactly once via onSessionExpired.

#### B7. Logout race: in-flight token refresh re-persists user + tokens after storage.clearAll, silently restoring the session on next launch
- **Where:** `mobile/src/context/AuthContext.tsx:105` · **Platform:** both · **Domain:** auth
- **What happens:** logout() clears AsyncStorage and the query cache but does not cancel or await the module-level refreshPromise in authedFetch. performRefresh, once past its storage.getRefreshToken() read, unconditionally saves the new tokens AND the user object when the response arrives (authedFetch.ts:113-117). Failure scenario: proactive refresh fires on app foreground (useProactiveRefresh.ts:90-97) or a background query hits a 401 and starts a refresh; the user taps Logout while it is in flight; clearAll() runs, then the refresh resolves and writes user + fresh access/refresh tokens back into storage. UI shows the login screen, but on the next cold start loadSession (AuthContext.tsx:74-84) finds savedUser + savedAccessToken and silently logs the 'logged-out' account back in — a real problem on shared devices. Fix: have performRefresh re-check that a refresh token still exists before saving, or invalidate/ignore the in-flight refresh on logout.
- **Trace:** mobile/src/hooks/useProactiveRefresh.ts:75 (getOrStartRefresh) -> mobile/src/lib/authedFetch.ts:73-122 (performRefresh in flight) -> mobile/src/context/AuthContext.tsx:97-108 (logout clearAll) -> authedFetch.ts:113-117 (saveTokens + saveUser AFTER clearAll) -> AuthContext.tsx:74-84 (next cold start restores session)
- **Root cause:** performRefresh persists session state based on a stale pre-fetch token read: mobile/src/lib/authedFetch.ts:113-117 saves tokens+user without re-checking that the stored refresh token still exists (logout's clearAll at mobile/src/context/AuthContext.tsx:105 may have run during the network round trip).
- **Fix:** In performRefresh, before the saveTokens/saveUser block (authedFetch.ts:113), re-read storage and bail if the session was invalidated mid-flight: `if ((await storage.getRefreshToken()) !== currentRefresh) return { ok: false, rejected: true };`. Single guard in the shared function covers all callers (proactive refresh, 401 retry, refreshSession); rejected:true routes concurrent callers through the idempotent onSessionExpired->logout path.

#### B13. Stale access-token override: after first token expiry every request 401s, spams /auth/refresh, and rate-limiting can force a spurious logout
- **Where:** `mobile/src/lib/authedFetch.ts:212` · **Platform:** both · **Domain:** platform-infra
- **What happens:** Screens pass `accessToken` from AuthContext React state as an explicit token override to every service call.
